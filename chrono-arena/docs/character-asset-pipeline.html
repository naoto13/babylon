キャラクターアセット制作パイプライン

Chrono Arena のキャラクターを「ねんどろいど風デフォルメの三面図」から リグ付き 3D アセットまで作る手順と、そこに至るまでの実測知見をまとめる。 写実系の参照画像から作る初期案は品質が要求に届かず打ち切った。その失敗も 再発防止のために記録する。

1. パイプライン全体

三面図を生成→ 正面を切り出す→ SPAR3D で 3D 化→ Voxel Remesh→ UV 再展開→ 三面図を投影→ リグ＋スキニング

各工程は独立したスクリプトになっており、途中から再実行できる。 新しいキャラクターを追加する場合も同じ手順をなぞれば足りる。

なぜデフォルメなのか。 image-to-3D は「見えている面を立体に起こす」処理なので、参照画像の情報量が 多いほど推測の余地が増えて破綻する。写実系の高精細な参照画像では、 テクスチャが白飛びして意匠が消え、実機では「のっぺりした黒い塊」になった。 デフォルメは形状の情報量が少ないぶん生成が正確になり、 本作のようにキャラが画面高の約 1/10 しか占めないゲームでは シルエットが読めることのほうが効く。

2. 画像生成プロンプトの定型

成果物の品質はここでほぼ決まる。以下の 4 ブロックは省略すると必ず破綻する。 gen-image スキル（codex 経由の gpt-image-2）で使う。

共通様式（全キャラで一字一句共有する）

ねんどろいど（Nendoroid）風のデフォルメ3Dフィギュアのキャラクターデザイン三面図。
頭身は約2.5頭身で、頭が大きく体は小さく、全体に丸みのあるフォルム。
手足は短くずんぐりしている。ディテールは大胆に省略し、少ない要素で意匠が読めるようにする。
写実的な3Dレンダーの質感で、マットな樹脂とつや消し金属のフィギュアとして描く。

【姿勢の絶対条件】必ず A ポーズにする。両腕を体側から左右へ約45度開き、
腕・脇・手のすべてが胴体から明確に離れて、腕と胴の間に背景がはっきり見える隙間を作る。
左右の脚も肩幅以上に開き、脚と脚の間にも背景の隙間を作る。
3つのビューとも同じ A ポーズにする。腕を体にくっつけたり、脚を閉じたりしてはならない。

【構図の絶対条件】1枚の画像の中に、同一キャラクターを
「正面向き」「真横向き（右を向く）」「背面向き」の順に左から右へ、
ちょうど3体だけ横一列に並べる。3体はすべて同じ高さ・同じ縮尺。
正投影（パースなし）。3体の間には背景がはっきり見える広い間隔を空ける。

【造形の絶対条件】すべての部位を厚みのある塊（ソリッド）として造形する。
板状・膜状・薄片・半透明の要素は一切作らない。
禁止: 翼、羽根、マント、なびく布、ケープ、リボン、鎖、触手、細い紐、
透明や半透明のパーツ、格子、透かし彫り、細長く飛び出す装飾。
装飾は本体に密着した厚い装甲か丸みのある塊で表現する。
角だけは例外だが、太く短い円錐形の塊にする。

【厳禁】4体以上並べること。歩行や走行などの連続したポーズ。
ピクセルアート・ドット絵・2Dイラスト。文字・矢印・ロゴ。影・床・グリッド線。武器や持ち物。

背景は均一な明るいグレー。全体をやや明るめの露出で描き、
黒い部位も真っ黒に潰さず面の形が読める明度を保つ。

意匠は「ハイテク・オカルト」（黒曜石と暗銀の未来装甲に発光する魔法回路が走る SF＋悪魔）。

各ブロックが必要な理由

ブロック省くとどうなるか
姿勢（A ポーズ） 腕を体側に下ろした姿勢だと SPAR3D が接触部を繋いでしまい、リグを入れたとき腕を動かすと胴が引っ張られて破綻する。T ポーズは真横から見ると腕が手前に突き出て体を隠すため、側面ビューからの投影が効かなくなる。A ポーズが最適。
構図（三面図） 「横一列に並べる」とだけ書くと、生成器が歩行アニメーションのスプライトシートを返してくる（実際に boss で発生）。「ちょうど3体だけ」「連続したポーズ禁止」の明記が要る。
造形（ソリッド） 翼・マント・薄い布は image-to-3D が立体に起こせず、テクスチャとして体に貼り付いて輪郭を濁らせる。画像の時点で作らせないのが唯一の確実な回避策。
露出（明るめ） 暗い意匠をそのまま渡すと SPAR3D のテクスチャベイクが部分的に、あるいは完全に失敗する（実測: 非黒率 0.06%＝ほぼ空のアトラス）。
生成器が指示を無視することがある。 まったく無関係な画像（ピクセルアートの猫、緑のフード弓使いの走行スプライト）が 返ってきた実績がある。透過率チェックも重複検出も通過して「正常終了」扱いになるため、 生成後は必ず目視する。失敗したら禁止事項を明記して再生成する。

3. スクリプトと実行手順

スクリプト役割
scripts/crop_turnaround_front.py三面図から正面ビューだけを切り出し、正方形にパディングする。背景色の推定、3ビューの分離、被写体の輝度チェックまで行う。
scripts/spar3d-run.shSPAR3D のラッパー。テクスチャ解像度を制御でき、複数画像をバッチ処理する。実行前にネイティブ拡張の CPU カーネル登録を診断する。
scripts/project_turnaround_texture.py三面図の 3 ビューを法線方向に応じてメッシュへ投影し、テクスチャを作り直す。SPAR3D が推測で埋めた背面・側面を正しい意匠に置き換える。
scripts/rig_nendo_character.pyVoxel Remesh → UV 再展開 → テクスチャ投影 → 16 ボーンのリグ構築 → 幾何ベースのスキニング → 検証ポーズのレンダー。
scripts/generate_arena_environment.pyアリーナの雰囲気を反映した IBL 環境マップ（equirectangular HDR）を生成する。
tools/asset-preview.html本編と同じアリーナ・カメラ・ライティング・GlowLayer でモデルを確認する検証ページ。新旧の比較、5 体並列表示に対応。

実行例（新キャラを 1 体作る）

# 1. 三面図を生成（上記プロンプトを使う）
#    → assets/production/demonic/turnarounds/<name>.png

# 2. 正面を切り出す
python3 scripts/crop_turnaround_front.py <name>

# 3. SPAR3D で 3D 化（1体あたり 20〜60秒、ピークメモリ約15GB）
TEXRES=1024 ./scripts/spar3d-run.sh assets/production/demonic/spar3d-nendo \
  assets/production/demonic/refs/<name>-nendo-front.png

# 4. 投影とリグの入力位置へ配置
cp assets/production/demonic/spar3d-nendo/<name>-nendo-front.glb \
   assets/production/demonic/spar3d/<name>-nendo.glb

# 5. リメッシュ・UV・投影・リグを一括で
blender --background --factory-startup --python-exit-code 1 \
  --python scripts/rig_nendo_character.py -- <name>-nendo

# 6. 検証
node ~/.claude/skills/image-to-3d-asset/scripts/check-glb.mjs \
  assets/production/demonic/rigged/<name>-nendo-rigged.glb
リグが不要で静的メッシュだけ欲しい場合は、5 の代わりに project_turnaround_texture.py を単体で実行する。 出力は assets/production/demonic/nendo/ に入る。

4. 品質の判定基準（実測値）

指標基準根拠
三面図の被写体平均輝度 0.20 以上（最低 0.15） 0.15 を下回るとテクスチャベイクが失敗しやすい。実測で 0.28 前後なら安定して成功する。
生成テクスチャの非黒率 50% 以上 成功時は 52〜64%。失敗時は 0.06%（ほぼ空）や 19.8%（部分的）になる。check-glb.mjs はこれを見ないので別途測る。
充填率（体積÷bbox体積） デフォルメで 28〜37% 塊で構成された造形の正常値。写実系の細身キャラでは 5〜10% だった。
baseColor の平均輝度 0.26〜0.34 本編のライティングは暗い（HemisphericLight 0.92 ＋ DirectionalLight 1.4、fog EXP2 0.014）。0.11〜0.16 で作ると実機で真っ黒な塊になる。
発光面積 2〜5.5% GlowLayer（intensity 0.62）と合わさるため、広くすると全身が発光色に染まって装甲の色分けが見えなくなる。
ボーン数 16 ねんどろいど体型では人体比率のボーン数を入れると関節が分離しない（後述）。
面数 hero 60,000 以下／敵は 15,000〜20,000 目安 敵は最大 74 体が同時に出現し、全メッシュが影のキャスターに登録される。

5. 落とし穴

SPAR3D はアルベドを一定明度に正規化する

暗い意匠（黒い装甲＋発光ライン）を渡すと出力テクスチャが白飛びして意匠が失われる。 参照画像側では解決できない。実測: 参照画像を gamma 0.45 で持ち上げて 平均輝度 0.216 → 0.453 にしても、出力テクスチャの平均輝度は 0.383 → 0.369 とほぼ不変だった。 白飛びしたテクスチャの彩度を上げて色を戻そうとすると、カラフルなノイズになって破綻する。

出力メッシュは非連結サーフェスに断片化している

見た目は繋がっていても、内部的には多数の独立した面の集まりになっている（hero で 1,386 個）。 Blender の自動ウェイト（Bone Heat）は連結メッシュ上の熱拡散を解く方式なので、 この状態では安定したウェイトが出せず、腕を上げると脇から扇状の伸び面が出る。 リグの前に Voxel Remesh で単一連結体にすることが前提条件。 リメッシュで元の UV は失われるため、UV 再展開とテクスチャ再投影がセットで必要になる。

三面図の 3 ビュー分離は連結成分だけでは失敗する

体の間隔が狭いキャラでは背景の列が一本も残らず、隣の体とつながって検出される。 対策は列ごとの被写体ピクセル数の谷（＝体の切れ目）で分割し直すこと。 crop_turnaround_front.py と project_turnaround_texture.py の 両方に実装が要る（片方だけ直すともう片方で同じエラーが出る）。

Blender のプレビューで明暗を判断してはいけない

Blender で「ちょうどよい」明るさにすると、本編のライティングでは大幅に沈む。 逆に、意匠照合のために明るい背景でレンダーすると、正しいテクスチャが白飛びして 「壊れている」と誤診する。どちらも実際に起きた。 明暗の判断は必ず tools/asset-preview.html（本編と同条件）で行う。

albedo を黒くしすぎると何を足しても見えない

ノーマルマップ・ORM マップ・IBL をすべて入れても装甲がのっぺりしたままだった原因は、 albedo が黒すぎたことだった。albedo を 5 倍にした瞬間にパネル分割・トリム・ フードの構造が一気に読めるようになった。 AAA 級のゲームでも黒い鎧を真っ黒には塗らず、中間調のガンメタルにして 環境光とリムライトで黒く見せる。

金属は「映すもの」がないと金属に見えない

PBR において金属の見た目はほぼ全てが環境の反射である。 scene.environmentTexture が無い状態で metallic 0.8〜0.94 を設定しても、 反射する対象がないため単色の平面として描画される。IBL の導入は工数が小さく効果が最も大きい。

6. リグの設計

16 ボーン構成

Root
└─ Hips → Spine → Chest → Neck → Head
   ├─ UpperArm.L → LowerArm.L      （肩当ては UpperArm、拳は LowerArm に含める）
   ├─ UpperArm.R → LowerArm.R
   ├─ UpperLeg.L → LowerLeg.L → Foot.L
   └─ UpperLeg.R → LowerLeg.R → Foot.R
デフォルメに人体と同じボーン数を入れると破綻する。 ねんどろいど体型は腕長が全高の 2 割程度しかないため、 Shoulder / UpperArm / LowerArm / Hand の 4 ボーンだと 1 本あたり数センチになり、 ウェイトが混ざって関節が分離しない（腕を上げるポーズと肘を曲げるポーズが ほぼ同じ見た目になる）。腕は 2 分割に減らす。 ねんどろいどの実物も肘関節を持たないものが多く、造形の考え方とも合う。 脚は歩行に膝が要るので 3 段を維持する。

ウェイトは幾何ベースで計算する

  • 各ボーンを線分（head → tail）として扱い、頂点からの最短距離 d を求める
  • ウェイト w = 1 / (d + eps)^p（p は 3〜5）
  • 上位 4 ボーンだけ残して正規化（glTF の 4 骨上限）
  • 左右の取り違えを防ぐため、頂点の X 座標の符号で割り当て先を制限する
  • 頭部は Head ボーンに 1.0 で固定する（デフォルメは頭が大きく、胴のウェイトを拾いやすい）

ボーン位置の比率（全高を 1.0 として足元から）

部位高さ部位高さ
足首0.06胸0.46
膝0.16肩0.54
股0.28首0.58
腰0.34頭中心0.78

頂点分布からの自動推定は、頭が全高の 4 割を占めるデフォルメでは外れる。 体型比率を定数として持つほうが確実。

7. 検証の作法

統計だけを合格条件にすると「パス詐欺」が起きる。 実例: 参照画像をメッシュへ投影する実装で、彩度と色相ビン数の統計はパスしたが、 実際は baseColor の 1 つの UV 島に全身像がそのまま貼られており投影は破綻していた。 統計は「色が複数あるか」しか測れず「正しい位置にあるか」を測らない。

作業を委任するときの条件設定

  • 位置の正しさが要件なら、生成物の画像を必ず自分で見る。数値指標で代替しない
  • リグの検証は「破綻がないこと」ではなく「ポーズごとに形が明確に変わること」を条件にする。比較すべき 2 枚を指定し、どこがどう違うかを具体的に述べさせる
  • ポーズの振り幅は大きくとる（腕上げは 60 度でなく 90 度、肘は下位ボーンだけを 90 度曲げて上位は固定）
  • テクスチャを貼った状態でレンダーさせる（グレーの粘土状態では破綻が見えにくい）

ブラウザでの実機確認

tools/asset-preview.html に window.__preview を露出してあるので、 javascript_tool からマテリアルやライトを直接書き換えて原因を切り分けられる。 Blender で再生成して往復するより桁違いに速い（実測: 3 回の再生成で分からなかった原因が JS 2 本で確定した）。 

// albedo が原因かを 1 行で切り分ける
const s = window.__preview.scene;
s.materials.forEach(m => m.albedoColor?.scaleInPlace(5));
s.render(); s.render();
動きを伴う確認は orca 埋め込みブラウザで行う。 claude-in-chrome のタブは visibilityState: "hidden" になり、 Chrome が requestAnimationFrame を止めるため engine.runRenderLoop が回らない。ゲームループが一切進まず、 しかもエラーは出ない（engine.getFps() は最後の値を返すので誤診しやすい）。 実測では30秒待っても残り時間・撃破数・HP が初期値のままだった。 rAF を setTimeout へ差し替えても、 エンジンが生成時にバインド済みなので効かない。

同じページを orca で開くと visibilityState: "visible" になり、 そのまま回る（実測 1502ms で 66 フレーム）。判定は次の 1 行で足りる。 

JSON.stringify({ visible: document.visibilityState, hasFocus: document.hasFocus() })

orca での確認手順

orca tab create --url "http://127.0.0.1:5173/?visual-test&auto-start" --json
orca eval --expression "window.__game.camera.fov = 0.95" --json
orca screenshot --format png --json | python3 -c "
import sys, json, base64, pathlib
r = json.load(sys.stdin).get('result', {})
b64 = r.get('data') or r.get('screenshot') or r.get('image') or ''
pathlib.Path('shot.png').write_bytes(base64.b64decode(b64))
"
本編には開発時限定のデバッグ窓口を用意してある。 ?visual-test を付けると window.__game に scene / engine / camera / player / enemies が露出し、 orca eval からカメラを引く・敵のクールダウンを 0 にして 任意のタイミングで攻撃を発火させる、といった操作ができる。 ?auto-start / ?enemy-preview=<type> / ?swarm=N / ?crowded / ?lightning-preview=shooter|boss も使える。
orca ブラウザの制約。 ビューポートは固定（実測 456×786）で window.resizeTo() は効かない。 全体を写したいときはページ側のカメラを操作する。 また 0.2 秒程度の短い演出は orca screenshot の間隔ではすり抜けるので、 開発用フラグで演出を引き延ばすか、状態を直接操作して発火タイミングを掴む。

8. 到達点と残課題

確立できたこと。 三面図からリグ付き 3D アセットまでの全工程がスクリプト化され、 新キャラの追加は同じ手順で通せる。hero で end-to-end の実証を完了した。

本編の状態

本編は現行モデル（配色改修済み）で動作している。 ねんどろいど版はまだ組み込んでいない。シーン側には IBL・ACES トーンマッピング・ SSAO・リムライトを導入済みで、これは新旧どちらのモデルにも効く。

残課題

  • 造形の粗さ — Voxel Remesh の代償で腕が溶けており、上腕と前腕の段差や指が潰れている。本編の俯瞰カメラでは判別できないが、近接カットを入れるなら作り直しが要る
  • 敵 4 体のリグ — 静的メッシュはあるがリグ未着手。同じパイプラインで通せる
  • アニメーション — 16 ボーンのリグができたので、Idle / Run / Attack / Dash / Hit / FutureSlash を作れる状態
  • 本編への組み込み — src/main.js の assetPaths 差し替えとスケール調整で切り替わる。loadModelAssets() はアニメーションクリップが揃わないと throw する設計なので、アニメーションが先に要る

打ち切った経路（再挑戦しないため）

  • 写実系の参照画像からの生成 — テクスチャが白飛びして意匠が消え、実機で現行モデルに及ばなかった。3 方式（そのまま利用／単色ティント／参照画像投影）すべて失敗
  • Mixamo でのオートリグ — Adobe ログインが必須でエージェント側から実行できず、2.5 頭身が人型と認識されるかも不確実。自前リグで代替した
