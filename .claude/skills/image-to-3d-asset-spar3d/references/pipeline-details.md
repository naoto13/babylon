# パイプライン詳細（参照画像定型の理由・落とし穴・減量実測）

SKILL.md の要点の背景にある「なぜそうするか」と、実測で踏んだ地雷の詳細。
（旧 SPAR3D 単独スキル本文からの移植。生成器は SPAR3D 固有だが、①参照画像・③検証・
④減量・⑤配置の各工程は生成器に依存せず TRELLIS.2 経路でもそのまま現役）

## 向く対象・向かない対象

テクスチャ付きで生成できる経路が使えるなら、**装飾的なプロップはほぼすべて AI 生成が有利**。
参照画像の意匠がテクスチャとして保存されるため、手続き生成 + 汎用マテリアルでは原理的に
出せない情報量が乗る。実測でも、単純な木の板や乳鉢のような地味な対象ですら、質感が付いた
瞬間に見違えた。

向かないのは2種類:

- **寸法が意味を持つもの** — 当たり判定そのもの、タイリングする建築物、UI用の板、正確な
  寸法比が要る機構。手続き生成やモデリングの方が速く確実。生成物は寸法がばらつくので、
  当たり判定は別途プリミティブで持つ設計にする
- **細い開放構造** — アーミラリ天球儀のリング、鳥籠、格子、鎖、蜘蛛の巣。生成器が最も苦手と
  する形状で、塊に潰れるか穴が埋まる。**やるなら参照画像側で対策する**: リングや骨組みを
  実物より太くデフォルメし、構造が読める角度（やや上から見下ろす等）を指定する。生成後は
  充填率で潰れを確認する（`tools/asset-pipeline/check-glb.mjs` が出す）

形状のみ（テクスチャなし）の生成器しか使えない場合は、有機的・装飾的な主役級だけに絞る方が
費用対効果が良い。

## 参照画像プロンプト定型（理由付き）

この定型が品質を大きく左右する。要素を削ると生成3Dが崩れやすい。

```text
共通様式: <作品のアートスタイル>の3Dプロップ参照画像。
単一オブジェクト（または一体化した小群）のみ、画面中央、斜め45度の3/4ビュー、全体が完全に収まる。
背景は完全な透明（アルファチャンネルの真の透過PNG）。均一で柔らかい照明。
色付きドラマチック照明・文字・ロゴ・人物は入れない。
画像内容: <対象物の具体的な説明。素材・色・装飾・形状の特徴>
```

各指定の理由:

- **3/4ビュー**: 正面のみだと奥行きが推測できず板状になる。真横・真上も同様に情報が足りない
- **透過背景**: 生成器は背景除去（rembg）を内蔵するが、自前で透過を渡す方が輪郭が正確。
  不透明背景でも動くが、床の影や壁を物体の一部と誤認することがある
- **均一照明**: 強い陰影はテクスチャに焼き込まれてしまう。ゲーム側でライティングするなら、
  素の色情報が欲しい
- **単一オブジェクト**: 複数物体は1つのメッシュに融合されて破綻する。「3本まとまった瓶」の
  ように**一体の群として意図する**場合のみ複数可
- **文字なし**: 判読不能な文字が焼き込まれて安っぽくなる。装飾的な線として指示する方が良い

`tools/asset-pipeline/gen-ref-image.sh` が gen-image スキル（codex + gpt-image-2）経由で
この定型を適用する。他の画像生成手段でも定型さえ守れば結果は同等。

手持ち画像を使う場合: 背景が複雑・被写体が小さい・強い影があるなら、先に切り抜くか背景差し
替えで生成し直す方が結局速い。

同じシーンに並べるアセットは、**同じ様式指定の文言を全アセットで共有する**。1体だけ写実、
1体だけトゥーンになると場が壊れる。

## 検証で見るべき点（詳細）

```bash
node tools/asset-pipeline/check-glb.mjs <生成された.glb>   # リポジトリルートで実行
```

- **TEXCOORD_0 と images がある** → テクスチャ付き。そのままマテリアルを使える
- **POSITION のみ** → UV も法線もない白メッシュ。アプリ側で法線再計算 + トライプラナー投影
  などの手当てが要る（`tools/asset-pipeline/integration.md`）
- **頂点数が10万超** → 減量を検討
- **bbox が極端に扁平** → 生成が板状に崩れている。参照画像かモデル選択を見直す
- **充填率**（体積 ÷ bbox体積）→ 開放構造の潰れ検出。リングや取っ手のある物は5〜25%に出る。
  骨組みを意図したのに45%超なら中身が詰まった塊。壺や球のような塊は高くて正常

## 減量（gltfpack 実測）

Web配信ならサイズ予算を先に決める。目安: 小物1MB以下、主役級3MB以下、シーン全体で20〜40MB。

```bash
pnpm dlx gltfpack -i in.glb -o out.glb -si 0.2   # 面数を20%へ簡約 + 量子化
pnpm dlx gltfpack -i in.glb -o out.glb           # 量子化のみ（形状はそのまま）
```

`-si` は0.1〜0.3が実用域。実測では 17.8MB/100万面 → 2.7MB/18万面 で見た目の劣化はほぼ判別
不能だった。テクスチャ付き glb を強く簡約するとUVが乱れることがある。減量後は必ず再検証し、
可能ならアプリ上で目視する（gltfpack 固有の罠は glb-compression-pipeline スキル参照）。

## 落とし穴（実測で踏んだもの）

- **生成が板状レリーフになる** — 参照画像が正面すぎるか、生成器側の設定が簡易モードに落ちて
  いる。3/4ビューの画像で再生成する
- **同じ参照画像なのに前のアセットと同一のglbが出る** — バッチスクリプトの変数取り違えなど、
  こちら側の事故を疑う。`shasum` で重複を確認する癖をつける
- **ブラウザで差し替えたはずのglbが反映されない** — 静的サーバのキャッシュ。開発中は
  no-store ヘッダを返すサーバを使う（`tools/asset-pipeline/integration.md` にワンライナー）
- **クラウド生成が突然エラーになり続ける** — 無料GPU枠の枯渇がほとんど。認証トークンを
  付けると解消することがある。リトライは間隔を空ける（連打は無意味）
- **ローカル生成が「CPUバックエンド未実装」で落ちる** — ネイティブ拡張が誤った環境でビルド
  されている。`spar3d-setup.md` の再ビルド手順を参照
- **手前に置いたアセットが画面に映らない** — 固定カメラの画角外。ワールド座標の勘に頼らず、
  実際にレンダリングして確認しながら詰める

## 量産のコツ

- 参照画像生成は**並列**で回せる（画像生成は独立）。3D生成は同一GPU/メモリを使うので
  **直列**が安全
- 1体ごとに検証を挟むより、バッチで全部作ってから一括検証する方が速い
- 失敗した1〜2体は後でまとめて作り直す。バッチ全体をやり直さない
- 生成した glb と参照画像はセットでリポジトリに入れる（再現性のため。参照画像は数百KB〜2MB
  なので許容範囲）
